# Laporan Analisis Keamanan & Autentikasi (QA)

Berdasarkan pengecekan terhadap sistem autentikasi, manajemen token, dan pengaturan route pada aplikasi, berikut adalah hasil analisis mengenai penyebab terjadinya respons `Unauthenticated` dan mengapa tabel `personal_access_tokens` seakan tidak terupdate.

## 1. Temuan Analisis

### A. Penyebab Semua Route API Memberikan Response `Unauthenticated`
Hampir seluruh route API (seperti `/logout`, `/products`, `/raw-materials`, dsb.) dibungkus oleh middleware `auth:sanctum` di dalam file `routes/api.php`. 
Sistem Sanctum membutuhkan autentikasi berbasis Bearer Token. Jika setiap kali route dipanggil klien menerima response `{"message": "Unauthenticated."}`, ini terjadi karena:
- **Klien (Postman/Frontend) tidak mengirimkan token** hasil dari proses login pada HTTP Header, atau token yang dikirimkan salah/sudah tidak valid.
- Middleware `auth:sanctum` akan memblokir request apa pun yang tidak memiliki header `Authorization: Bearer <token_auth>` dan otomatis mengembalikan pesan `Unauthenticated`.

### B. Penyebab Tabel `personal_access_token` Tidak Terupdate Saat Login
Di dalam `app/Http/Controllers/Api/AuthController.php` (pada method `login`), terdapat logika berikut:
```php
$user->tokens()->where('name', $request->device_name)->delete();
$token = $user->createToken($request->device_name, $abilities)->plainTextToken;
```
Ketika seorang user login, sistem akan **mencari dan menghapus token lama** yang memiliki nama perangkat (`device_name`) yang sama, baru kemudian membuat token baru. 
- **Efek saat testing:** Jika Anda login berkali-kali menggunakan `device_name` yang sama (misal: "web"), baris di tabel `personal_access_tokens` akan dihapus lalu ditambah lagi satu. Jumlah barisnya tidak akan bertambah. Hal ini seringkali menimbulkan ilusi bahwa "tabel tidak terupdate", padahal tokennya terus diperbarui dan diganti dengan data baru.

### C. Penyebab Tabel `personal_access_token` Tidak Terupdate Saat Logout
Pada file `routes/api.php`, endpoint `/logout` dilindungi oleh middleware:
```php
Route::middleware(['auth:sanctum', ExtendTokenActivity::class])->group(function () {
    Route::post('/logout', [AuthController::class, 'logout']);
});
```
Jika Anda memanggil endpoint `/logout` **tanpa menyertakan Bearer Token** yang valid di header, request tersebut akan **diblokir oleh middleware `auth:sanctum`** dan langsung mengembalikan pesan `Unauthenticated`.
- Karena ditolak di tahap awal (middleware), sistem **tidak pernah masuk ke Controller** (`AuthController@logout`).
- Alhasil, perintah penghapusan token dari database (`$request->user()->currentAccessToken()->delete();`) tidak pernah dijalankan, sehingga token lama masih tetap berada di dalam tabel `personal_access_tokens`.

## 2. Saran Perbaikan dan Cara Pengujian

### Cara Pengujian yang Benar (Untuk QA / Tester)
Agar proses pengujian login, logout, dan pemisahan role berjalan lancar, ikuti standar pengiriman request:
1. **Lakukan Login:** Lakukan POST ke `/login` dan copy `token` yang ada di dalam block response data.
2. **Setiap Akses Route yang Dilindungi (termasuk `/logout`):** Tambahkan konfigurasi HTTP Header berikut pada Postman/Insomnia:
   - `Authorization` : `Bearer <paste_token_disini>`
   - `Accept` : `application/json`

### Saran Perbaikan Kode (Untuk Developer)
Sistem dasar sudah berjalan dengan baik, namun terdapat sedikit rekomendasi penyesuaian penulisan:
1. **Perbaikan Penulisan di Middleware:**
   Pada file `app/Http/Middleware/ExtendTokenActivity.php`, pemanggilan fungsi ditulis `$token->ForceFill(...)`. Walau di PHP tidak menyebabkan error (*case-insensitive*), sangat direkomendasikan menulisnya dengan format *camelCase* sesuai standar Laravel:
   ```php
   // Sebaiknya ubah:
   $token->ForceFill(['last_used_at' => now()])->save();
   
   // Menjadi:
   $token->forceFill(['last_used_at' => now()])->save();
   ```

2. **Implementasi Ability / Role:**
   Pemberian variabel `$abilities` berdasarkan role di dalam proses login sudah sangat bagus. Untuk memaksimalkan keamanan (pemisahan role), pastikan developer menambahkan middleware cek *ability* pada grup route terkait. 
   Contoh di `api.php`:
   ```php
   Route::middleware(['auth:sanctum', 'ability:manage:products'])->group(function () {
       Route::post('/products', [ProductController::class, 'store']);
   });
   ```
   *(Saat ini, middleware `ability` sudah diregistrasi di `bootstrap/app.php`, hanya perlu dipasangkan ke route yang spesifik agar user kasir tidak bisa memanipulasi produk).*
