## E. Login & Authentication Findings  
### BUG‑001 – Login succeeds but employee role blocked after authentication
- **Title**: Employee users cannot stay logged in – forced logout after Auth::attempt
- **Category**: Login
- **Severity**: HIGH
- **Status**: Confirmed
- **Location**: `app/Http/Controllers/Web/AuthController.php:31‑36`
- **Reproduction Steps**: 1. Seed an employee user (see BUG‑004). 2. Attempt login with correct credentials. 3. Auth succeeds but immediately logs out and redirects back with error “Access denied. Karyawan tidak diizinkan memasuki panel admin.”
- **Expected**: Successful login for all valid credentials, with role‑based navigation after login.
- **Actual**: Employee role is explicitly rejected, causing a confusing “Access denied” error after a successful password check.
- **Evidence**: Code excerpt lines 31‑36 in `AuthController.php`.
- **Likely Root Cause**: Business rule hard‑coded in controller rather than central middleware; may be unintended for “cashier” role also.
- **Impact**: Prevents employees from using the admin panel; may affect legitimate staff workflows.
- **Recommended Fix Direction**: Move role‑based denial to middleware (`CheckWebRole`) and make the rule configurable; ensure the UI clearly communications allowed roles.
- **Confidence**: HIGH

Additional observations: CSRF token is rendered correctly; validation rules are correct; “Remember me” checkbox is present but not processed.

## F. Role & Authorization Findings  
### BUG‑002 – CheckWebRole incorrectly logs out *cashier* users
- **Title**: Cashier role treated as unauthorized in middleware
- **Category**: Authorization
- **Severity**: HIGH
- **Status**: Confirmed
- **Location**: `app/Http/Middleware/CheckWebRole.php:19‑24`
- **Reproduction Steps**: 1. Seed a cashier user (uncomment cashier block in `UserRoleSeeder`). 2. Log in as cashier. 3. Middleware logs out and redirects to login with “Akses ditolak …”.
- **Expected**: Cashier should be allowed to access routes protected by `role:owner,admin` only if explicitly permitted, otherwise receive a 403, not a forced logout.
- **Actual**: Middleware performs logout, destroying session and confusing user.
- **Evidence**: Code excerpt lines 19‑24.
- **Likely Root Cause**: Middleware conflates “unauthorized” with “logout” – should `abort(403)` instead.
- **Impact**: Session is destroyed, causing loss of unsaved work and poor UX.
- **Recommended Fix Direction**: Replace `Auth::logout()` with `abort(403, 'Access denied')` or redirect with a proper error message; keep session intact.
- **Confidence**: HIGH

### BUG‑005 – Role parameter parsing may fail
- **Title**: `role:owner,admin` may be passed as a single string, causing `in_array` check to always fail
- **Category**: Authorization
- **Severity**: MEDIUM
- **Status**: Potential
- **Location**: `routes/web.php` (middleware declaration) & `CheckWebRole.php` (parameter handling)
- **Reproduction Steps**: 1. Log in as admin. 2. Access a route inside the middleware group. 3. Observe if access is granted (it is, because admin bypasses early check). 4. Change the middleware to `role:owner,admin` with a custom test for a role that is not listed (e.g., a new “manager” role) and see if request is aborted.
- **Expected**: Middleware should accept multiple roles separated by commas.
- **Actual**: Laravel passes the whole string `"owner,admin"` as a single argument; `in_array($user->role, $roles)` will never match unless the role string includes the comma.
- **Evidence**: Code in `CheckWebRole.php` uses `$roles` directly without splitting.
- **Likely Root Cause**: Misunderstanding of Laravel’s middleware parameter handling.
- **Impact**: Potential unauthorized access if a role other than `owner` or `admin` is inadvertently allowed.
- **Recommended Fix Direction**: Split the parameter: `foreach (explode(',', $roles[0]) as $role) { … }` or use a dedicated package like Spatie’s permission.
- **Confidence**: MEDIUM

Additional observations: No dedicated `owner`‑only middleware block – an empty group is defined at lines 52‑55 in `web.php`. The `role` column is a simple string; no role hierarchy or permission system is present.
